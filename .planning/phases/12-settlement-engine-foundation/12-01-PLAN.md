<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Paystack webhook → settlement caller → SettlementService | Webhook payload is untrusted input; by the time it reaches `SettlementService.settle()`, every `recipients[].walletId` must already be server-side resolved by the caller (never taken from webhook `metadata`) |
| SettlementService → Postgres | Wallet mutation boundary — every write must be lock-protected and idempotent |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-12-01 | Repudiation/Tampering | `SettlementService.settle()` idempotency precheck | mitigate | `Transaction.reference @unique` DB constraint is the authoritative guard; `startsWith` precheck is a fast-path optimization only — see T-12-02 for the race case |
| T-12-02 | Tampering/Elevation of Privilege | `SettlementService.settle()` concurrent duplicate webhook delivery | mitigate | Catch `Prisma.PrismaClientKnownRequestError` with `code === 'P2002'` inside the `$transaction` catch block and treat as benign replay (no refund, no rethrow-as-failure) — closes the Pitfall 1 race window where two near-simultaneous webhook deliveries could otherwise trigger a spurious refund on an already-settled payment |
| T-12-03 | Tampering | Drift/rounding manipulation across many small settlements | mitigate | `Math.abs(drift) > 0.02` throws before any wallet write; platform wallet always absorbs legitimate rounding remainder, never a recipient |
| T-12-04 | Information Disclosure | Ministry wallet id caching | mitigate | `resolveMinistryWallet()` reads `PlatformConfig` fresh on every call — never cached — so an operator rotating the Ministry wallet takes effect immediately, and no stale wallet id is retained in process memory across a config change |
| T-12-05 | Denial of Service | Large recipient count holding a Postgres connection during `$transaction` | accept | Documented ceiling (Prisma default `timeout: 5000ms`); this phase's callers max out at 5 recipients (Tour); revisit only if a future caller needs a larger N (RESEARCH.md Pitfall 3) |
</threat_model>
