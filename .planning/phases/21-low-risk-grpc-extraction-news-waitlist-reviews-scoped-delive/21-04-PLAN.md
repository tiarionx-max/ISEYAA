<objective>
Begin the Reviews extraction — position 3 in the D-05 risk-ascending order, the first of the 4 services with a genuine cross-domain write (the debounced rating recompute writes into `TourGuide`/`TourPackage`/`Property`). This plan lands the server-side gRPC app (`reviews-service`) and splits `ReviewsAdminController` out of `ReviewsModule` into its own new `ReviewsAdminModule`, so that when `reviews-service` wholesale-imports `ReviewsModule` (Task 1), it does NOT also transitively expose the admin controller's HTTP routes inside the new gRPC process. Plan 21-05 completes the split by moving the public `ReviewsController` into a new `reviews-client` module and wiring the monolith end-to-end.

Per CONTEXT.md D-07, `ResolveReviewFlag`'s proto request has no `decision`/`resolution` fields — the researched resolution is that `resolveFlag` (along with `getFlagQueue`/`getFlag`, which have zero proto coverage at all) stays fully in-process, calling `ReviewsService`/Prisma directly. This plan's module split is what makes that "stays in-process, cleanly separated" outcome actually true at the process-boundary level, not just at the code level.

Purpose: Land reviews-service and the admin/public controller module split before Plan 21-05 adds the client-side shape-reconciliation logic (photos write-back, user-embed enrichment, in-memory pagination).
Output: `backend/apps/reviews-service/` (new independently-buildable NestJS app) + `backend/src/modules/reviews/reviews-admin.module.ts` (new) + updated `reviews.module.ts`/`app.module.ts`.
</objective>
