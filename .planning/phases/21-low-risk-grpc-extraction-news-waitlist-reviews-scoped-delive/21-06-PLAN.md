<objective>
Extract Delivery's `VerifyDeliveryOtp` RPC — the highest-risk, final service in the D-05 rollout order, since it touches Redis+Postgres state (`delivery:otp:*` keys, `deliveryOrder.otpVerifiedAt`) that the still-in-process `DeliveryService` (RequestDelivery/AcceptDelivery/CompleteDelivery/DeliveryGateway) continues to read and write live.

Per D-01, `delivery-otp-service` reuses `DeliveryService` as-is (unmodified source, matching `notifications-service`'s precedent of not hand-rolling a lean extraction module). This plan makes TWO deliberate, narrow deviations from D-01's literal "import [X]Module wholesale" framing — both because a naive wholesale import would permanently change delivery-otp-service's final HTTP surface in ways nothing later in the roadmap undoes. First: `DeliveryModule`'s own `providers` array is `[DeliveryService, DeliveryGateway]` (see `backend/src/modules/delivery/delivery.module.ts`), and `DeliveryGateway` is a real `@WebSocketGateway()`-decorated Socket.IO server that NestJS's gateway discovery binds to whatever HTTP server exists in the process the moment the class is instantiated as a provider. Since `DeliveryGateway` is not exported from `DeliveryModule`, there is no way to override or exclude it from outside while still importing `DeliveryModule` itself — a wholesale import would always instantiate the real gateway, opening a second, live, JWT-accepting WebSocket endpoint inside delivery-otp-service, directly contradicting Roadmap Phase 21 Success Criteria #2 ("DeliveryGateway stays in-process/monolith-only"). Second: `DeliveryService`'s other constructor dependencies (`WalletService`, `S3Service`, `SettlementService`) live only in `WalletModule` and `CommonModule` — but `WalletModule` declares `controllers: [WalletController]` and `CommonModule` declares `controllers: [SettlementController, UploadController]`, and wholesale-importing either module would permanently mount those `@UseGuards(JwtAuthGuard)`-protected controllers onto delivery-otp-service's HTTP listener. Since this plan does not import `AuthModule` (no `JwtStrategy` is ever registered in this process — see below), every request to `/wallet/*`, `/settlements/*`, or `/uploads/*` on delivery-otp-service would throw Passport's "Unknown authentication strategy \"jwt\"" at runtime: an unintended, permanently-broken wallet-mutation surface (including `/wallet/topup` and `/wallet/transfer`) inside a service whose entire narrow-scope rationale (D-03) is "OTP verification only." D-01's own stated rationale was speed and precedent-fidelity over minimal blast radius — not "every provider AND every controller must ship no matter the cost" — so this plan instead: (a) provides `DeliveryService` directly in delivery-otp-service's own `app.module.ts`; (b) directly provides `WalletService`, `S3Service`, and `SettlementService` as bare `providers` entries (NOT via a `WalletModule`/`CommonModule` import) to satisfy `DeliveryService`'s constructor; (c) directly provides each of THOSE services' own constructor dependencies in turn — `PaystackService` (needed by `WalletService`, and transitively by `RefundService`), `RefundService` and `ReferenceService` (needed by `SettlementService` via `RefundService`) — so the full provider graph resolves with zero controllers attached; and (d) overrides the `DeliveryGateway` injection token with a no-op stub object so `DeliveryService`'s `@Inject(forwardRef(() => DeliveryGateway))` constructor parameter resolves without ever constructing the real gateway class. Net effect versus the original wholesale-import framing: `AuthModule`/`JwtModule`/`DeliveryController`/`WalletController`/`SettlementController`/`UploadController` no longer ship into this process at all — delivery-otp-service's ONLY controllers are `HealthController` and `DeliveryOtpGrpcController` — a strict reduction in blast radius, not an expansion.

This plan also resolves Pitfall 5 concretely rather than leaving it as an open assumption: by reading `node_modules/@nestjs/microservices/exceptions/base-rpc-exception-filter.js` directly, this phase confirms that NestJS's DEFAULT `@GrpcMethod` exception handling does NOT preserve a thrown `BadRequestException`'s message across the gRPC boundary — non-`RpcException` errors are replaced with the generic string `MESSAGES.UNKNOWN_EXCEPTION_MESSAGE` ("Internal server error"). Without an explicit fix, a driver who enters the wrong OTP would see "service unavailable" instead of "incorrect OTP, N attempts remaining" — this plan's gRPC controller task builds the fix (explicit `RpcException` wrap with a structured `{code, message}` payload) as its own first-class task, not an afterthought.

Purpose: Land the server side of the Delivery OTP extraction — reusing `DeliveryService` unmodified, excluding only the live `DeliveryGateway` binding that would otherwise violate the phase's in-process-only Gateway guarantee — including the one design element (business-exception-vs-transport-exception gRPC mapping) with no precedent anywhere else in this codebase.
Output: `backend/apps/delivery-otp-service/` (new independently-buildable NestJS app; directly provides `DeliveryService`, stubs `DeliveryGateway`).
</objective>
