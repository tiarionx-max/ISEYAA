<objective>
Close CR-01 and CR-02 (independently confirmed by 21-VERIFICATION.md as the ONLY 2 failed must-haves out of 10 in Phase 21's goal-backward verification). Both are the same class of regression: `reviews-grpc.controller.ts`'s `createReview` handler and `waitlist-grpc.controller.ts`'s `joinWaitlist` handler call their domain services with no `try/catch`, so business exceptions (`NotFoundException`/`ForbiddenException`/`BadRequestException`/`ConflictException`) are never wrapped in `RpcException`. NestJS's default `BaseRpcExceptionFilter` replaces any non-`RpcException` thrown across a `@GrpcMethod` boundary with a generic "Internal server error" message. On the client side, `reviews-client.service.ts` and `waitlist-client.service.ts`'s catch blocks never inspect `err.code`, so every failure — business-rule or genuine transport outage — becomes a generic `ServiceUnavailableException` (503). A citizen reviewing a tour booking they don't own gets 503 instead of 403; a duplicate review gets 503 instead of 409; an early review gets 503 instead of 400 with the real reason; a waitlist join with neither email nor phone gets 503 instead of 400 with "Provide an email or phone number".

The proven fix pattern already exists in this same phase: `backend/apps/delivery-otp-service/src/delivery-otp-grpc.controller.ts` (server-side explicit `RpcException({code, message})` wrap per exception type) and `backend/src/modules/delivery-otp-client/delivery-otp-client.service.ts` (client-side `err?.code === GrpcStatus.X` strict-equality mapping back to the matching Nest HTTP exception, falling back to `ServiceUnavailableException` only for unrecognized/transport codes). This plan mirrors that exact pattern for Reviews and Waitlist — no new architecture, no new approach.

Purpose: Restore Phase 21's explicit "zero client-visible behavior change" goal and GRPC-08's "zero REST behavior change" requirement text for the Reviews and Waitlist gRPC extractions.
Output: `reviews-grpc.controller.ts` + `reviews-client.service.ts` + `waitlist-grpc.controller.ts` + `waitlist-client.service.ts` all gain explicit business-exception-vs-transport-exception mapping across the gRPC boundary, each proven by a new/extended unit test that fails without the fix and passes with it.
</objective>

    }

}
