Note: backend/nest-cli.json's project map confirms each service's tsConfigPath and that no top-level "root" project override exists (the monolith's default `nest build` with no project arg uses tsconfig.build.json, untouched by this plan).

From backend/nest-cli.json: top-level `sourceRoot: "src"`, top-level `compilerOptions: { deleteOutDir: true }`, and a `projects` map with one entry per service, each shaped as `{ "type": "application", "root": "apps/<service>", "entryFile": "src/main", "sourceRoot": "apps/<service>/src", "compilerOptions": { "tsConfigPath": "apps/<service>/tsconfig.app.json" } }` for all 8 services (auth-service, wallet-service, events-service, stays-service, marketplace-service, admin-service, ai-service, notifications-service).

Critical inherited behavior: `deleteOutDir: true` at the top level applies to every project unless overridden (none of the 8 override it). Every `nest build <service>` DELETES the shared `backend/dist` output directory before compiling. This means: (a) `find backend/dist -name main.js` after a build only shows the JUST-BUILT service's output, not all previously-built services' — verify each service's output path immediately after that specific service's own build, not after running the full 8-service loop once; (b) this has zero effect on Docker builds since each service's Dockerfile builds in its own isolated container.

From backend/tsconfig.build.json (the monolith's own build config — DO NOT MODIFY): `{ "extends": "./tsconfig.json", "exclude": ["node_modules", "dist", "test", "**/*spec.ts", "apps"] }`. This inherits `rootDir: "./src"` and `outDir: "./dist"` unchanged from backend/tsconfig.json — the fix in this plan is applied ONLY at the per-service tsconfig.app.json level (not the shared base backend/tsconfig.json) specifically so the monolith's own build output path (backend/dist/main.js, referenced by backend/package.json's start:prod script) never shifts. This is the deliberate, lower-risk alternative documented in 10-PATTERNS.md (widening the shared base file was the other option research presented, but it would move the monolith's own compiled entry point from dist/main.js to dist/src/main.js, breaking the live Railway deployment's start command — out of scope per CLAUDE.md's "no runtime changes" constraint and this phase's explicit "no changes to the monolith's actual request-handling behavior").
</interfaces>
