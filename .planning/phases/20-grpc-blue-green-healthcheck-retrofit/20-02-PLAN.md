<objective>
Guard all 6 `@Cron` jobs GRPC-06b names (D-07) with `RedisService.setNx()`'s existing distributed-lock primitive, so two replicas briefly coexisting during a blue-green cutover's dual-liveness window cannot both execute the same scheduled job. `db-metrics.service.ts`'s `pollOpenConnections` is explicitly excluded (D-07 — local in-memory gauge only, no shared side effect).

Purpose: A blue-green cutover on Railway briefly runs old and new containers side-by-side. Every unlocked `@Cron` job in that window fires twice — for `releaseEscrow` (wallet credit) this is a real double-payout risk; for the heartbeat-cleanup and tour-notification crons it's wasted work / duplicate push sends. This phase closes that gap using the codebase's one existing (fail-open) lock primitive, no new infrastructure.
Output: 6 guarded cron methods across 4 service files, each with new unit test coverage proving the skip-and-return behavior and the fail-open guarantee.
</objective>

`async setNx(key: string, value: string, ttlSeconds: number): Promise<boolean>` — atomic `SET key value EX ttlSeconds NX`. Returns `true` if the lock was acquired (or if Redis is unavailable — optimistic fail-open, per the method's own doc comment). <threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Redis (Upstash) ↔ monolith cron scheduler | Distributed lock coordination substrate — shared across all replicas of the monolith process |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-20-04 | Denial of Service (self-inflicted stuck lock) | `RedisService.setNx()` lock keys across all 6 guarded crons | mitigate | Every TTL is set strictly below its cron's own interval (e.g. 25s lock on a 30s cron, 3300s lock on a 3600s cron) — a replica that crashes mid-tick leaves a stale lock that self-expires before the next legitimate tick ever runs, so no cron can be silently blocked "forever" as the security_context flags; this is the concrete mechanism, not a policy promise |
| T-20-05 | Repudiation (silent skip, no trace) | Skip-and-return branch in all 6 guarded methods | mitigate | Each skip logs via `this.logger.debug('<methodName>: lock held by another replica — skipping this tick')` — distinguishable from the method's existing `this.logger.error(...)` failure path in log aggregation |
| T-20-06 | Tampering / Elevation of Privilege | Lock keys are process-internal, not exposed via any API | accept | No external actor can read or write `cron-lock:*` keys; Redis access itself is already a closed internal trust boundary unaffected by this change |
</threat_model>
