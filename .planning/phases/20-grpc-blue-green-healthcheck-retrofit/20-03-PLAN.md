<objective>
Add the D-01 canary kill-switch flag to `NotificationsClientService` — the monolith's sole gRPC facade over `notifications-service` — and, in the same file set, fix the pre-existing `NotificationsClientModule` circular-dependency bug (D-09 folded scope) that this exact same code was about to gain new test coverage for.

Purpose: Per 20-RESEARCH.md's Critical Design Clarification, `notifications-service` is a single-hostname Railway service — there is no second live instance to literally "route to." The coherent, D-01-compliant design is a kill switch: when flipped off, the monolith immediately stops depending on notifications-service (reusing the exact `ServiceUnavailableException` degrade path it already throws on real gRPC failures), independent of whatever Railway is doing underneath. This kill-switch reading of D-01 is now the explicitly confirmed, locked decision — see 20-CONTEXT.md's D-10 addendum (added during planning revision), which resolves RESEARCH.md's Critical Design Clarification as accepted rather than left ambiguous. Fixing the circular dependency in the same plan is efficient (same two files) and is a prerequisite for this canary-flag work ever getting exercised by `test:e2e:tours` in CI (see 20-04-PLAN.md).
Output: A working `grpc.notifications_service.canary_enabled` kill switch, a zero-circular-dependency module graph, and full regression + new-case test coverage.
</objective>

CONFIRMED root cause (via `npx madge --circular --extensions ts --ts-config tsconfig.json src/app.module.ts` run against the current tree, and via a live `npm run test:e2e:tours` reproduction against a real Postgres/Redis — both done during planning, not guessed): the ONLY circular dependency in the entire `backend/src` graph is `notifications-client.module.ts` <-> `notifications-client.service.ts`. `notifications-client.module.ts` exports a `NOTIFICATIONS_PACKAGE` string constant AND imports `NotificationsClientService` (for its `providers` array); `notifications-client.service.ts` imports `NOTIFICATIONS_PACKAGE` back from `./notifications-client.module`. This is a plain CommonJS require-cycle between a module file and its own service file — NOT a two-module bidirectional `imports: [forwardRef(...)]` scenario (there is no such scenario anywhere in this codebase; `grep forwardRef` returns zero matches). The correct fix is extracting the constant to a new leaf file with zero imports, not adding `forwardRef()` anywhere.

Current `backend/src/modules/notifications-client/notifications-client.service.ts` (full file, 74 lines): `import { NOTIFICATIONS_PACKAGE } from './notifications-client.module';` (line 6) — this is the import that must move to the new constants file. SETTLE-09 precedent for the flag-read pattern (`backend/src/modules/delivery/delivery.service.ts:577-583`): `const cutoverCfg = await this.prisma.platformConfig.findUnique({ where: { key: 'delivery.settlement_engine_enabled' } }); const cutoverEnabled = cutoverCfg?.value === true;` — strict equality against `true`, never `Boolean(cfg.value)`. This plan's flag inverts the semantics (absence/anything-but-`false` means enabled, matching "safety brake on an already-live feature," per 20-RESEARCH.md's Critical Design Clarification, confirmed as the locked reading of D-01 via 20-CONTEXT.md's D-10 addendum) — so the correct check here is `cfg?.value !== false` (or equivalently `!(cfg && cfg.value === false)`), NOT the `=== true` pattern used by the settlement-engine flags, since those are opt-IN cutover flags and this one is an opt-OUT kill switch.

`PrismaService` is NOT currently injected into `NotificationsClientService` (it's a pure gRPC facade with no DB access today) — it must be added. `PrismaModule` is `@Global()`, so no `imports` array change is needed in `NotificationsClientModule`.
