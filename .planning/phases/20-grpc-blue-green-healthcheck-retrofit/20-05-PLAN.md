Exact sequencing this runbook MUST document, in order (per 20-RESEARCH.md's "System Architecture Diagram" and Pitfall 2 — do not reorder, the ordering itself is the load-bearing content):
1. Operator flips the canary flag OFF first: `PATCH /api/v1/admin/config/grpc.notifications_service.canary_enabled` with body `{ "value": false }` (existing endpoint, `backend/src/modules/admin/admin.controller.ts:96-100`, already `SUPER_ADMIN`/`LGA_ADMIN` + `JwtAuthGuard`-gated — no new auth work). This makes the monolith immediately stop depending on notifications-service (`NotificationsClientService` now throws `ServiceUnavailableException` per 20-03-PLAN.md), independent of whatever Railway does next.
2. Railway performs its own healthcheck-gated container swap for `notifications-service` underneath (deploy the new build; Railway's `healthcheckPath = /healthz`, wired in 20-01-PLAN.md, blocks promotion if the new container's health check fails).
3. Operator runs D-03's synthetic verification DIRECTLY against the new container — bypassing the monolith and the canary flag entirely (e.g. a raw gRPC health check call, plus a small number of known-safe test notification sends to an ops-owned test number/email). This step must explicitly NOT rely on the canary flag or the circuit breaker, since with the flag off, nothing is calling through those paths yet.
4. Operator flips the canary flag back ON: `PATCH .../canary_enabled` with `{ "value": true }`. The monolith resumes real citizen traffic through `notifications-service`.
5. Operator actively watches, for exactly 15 minutes (D-05, not passive/unattended): (a) the existing Grafana Cloud dashboard's gRPC error rate for `notifications-service`, and (b) `ResilienceService`'s `notificationsGrpc` circuit-breaker state (open = trouble) — explicitly note per Pitfall 2 that BOTH signals are only meaningful from this point forward, since step 1 made the monolith stop calling the service entirely; watching them before step 4 is meaningless (a flat/idle graph before the flag flips back on proves nothing).
6. Rollback path (if step 5 shows trouble): flip the flag back to `{ "value": false }` — this is the entire rollback mechanism (D-04, no new tooling). If the underlying code itself needs reverting (not just traffic paused), separately trigger a standard Railway rollback to the previous known-good deployment — an existing Railway platform capability, not something this phase builds.
