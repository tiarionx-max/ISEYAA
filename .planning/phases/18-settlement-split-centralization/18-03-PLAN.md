<objective>
Migrate the 3 "special-case" settlement call sites — Marketplace, Stays, Studio — off duplicated inline `platformConfig.findUnique()` reads onto `SettlementService.resolveSplit()`. Each has a locked constraint from CONTEXT.md that must be preserved exactly:

- **Marketplace (D-02):** the per-vendor `Vendor.govtLevyPct` override is NOT absorbed into the centralized resolver — it continues to be read directly from the `Vendor` row; only the module-level `platform_fee_pct` routes through `resolveSplit()`.
- **Stays (D-05 + RESEARCH.md's new finding):** `resolveSplit()` must be called at booking-creation time and its result stored on `Booking.govtLevyPct`, exactly as today — NOT moved into the `@Cron`-driven `releaseEscrow()` method, which would let a post-booking split-percentage change retroactively apply to bookings already priced during their (potentially multi-week) escrow hold.
- **Studio (D-01):** `platformFeePct` is fetched but never applied to the split math today (the platform silently absorbs 100% of the remainder) — the migrated `SettlementSplitTier` row's `platformPct` is `null` for Studio (set explicitly in `18-01`'s migration script), and this call site must preserve that exact "fetched but unused" behavior, NOT add an earner/HOST recipient to Studio's `settle()` call.

Purpose: closes out SETTLE-11a/b for the 3 remaining call sites, each requiring careful preservation of an existing, deliberate money-flow inconsistency rather than a "fix."

Output: `marketplace.service.ts`, `stays.service.ts`, `studio.service.ts` each call `resolveSplit()` exactly once at the correct point in their existing control flow; regression tests prove identical computed amounts before/after migration, plus a dedicated Stays test proving a mid-escrow-hold tier change does not retroactively affect an already-created booking.

This plan does NOT touch Transport, Delivery, Events (`18-02-PLAN.md`) or the admin CRUD endpoints (`18-04-PLAN.md`). All three plans depend only on `18-01` and touch disjoint files, so they run in parallel in Wave 2.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| `@OnEvent`/booking-creation handler → `resolveSplit()` | Internal call; input amounts (`total`, `totalPrice`) are server-computed from already-validated DB rows (Order/Booking/StudioBooking), never taken directly from untrusted webhook payload metadata |
| `resolveSplit()` result → `Booking.govtLevyPct` (Stays only) | Snapshot write at booking-creation time; subsequent config changes must never retroactively alter an already-created booking's stored percentage |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-------------------|
| T-18-07 | Tampering | Marketplace/Stays/Studio `resolveSplit()` call sites | mitigate | Inputs are server-computed amounts from validated DB rows, never from untrusted webhook metadata; resolver itself already guards non-finite config (`18-01`) |
| T-18-08 | Repudiation (money-flow-change risk) | `stays.service.ts` | mitigate | `resolveSplit()` call kept strictly at booking-creation time, never inside `releaseEscrow()` — a mid-escrow-hold split-percentage change cannot retroactively alter an already-priced booking; enforced by a dedicated regression test |
| T-18-09 | Tampering (scope-creep risk) | `studio.service.ts` recipients array | accept | D-01's "no earner recipient" behavior is a known, deliberately-preserved inconsistency, not a security gap — fixing it is explicitly out of scope for this phase; a regression test asserts the recipients array is not silently expanded |
</threat_model>
