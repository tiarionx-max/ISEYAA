<objective>
Establish the foundation for SETTLE-11: add the `SettlementSplitTier` Prisma model, add `SettlementService.resolveSplit()` (mirroring the existing `resolveMinistryWallet()` always-fresh-read pattern), add the `Number.isFinite()` NaN guard required by SETTLE-11d directly inside `settle()`, and backfill all 6 modules' currently-live `PlatformConfig` values into the new table via a dedicated one-off migration script.

This plan does NOT touch any of the 6 feature-service call sites (Transport/Delivery/Marketplace/Events/Stays/Studio) — those are migrated in `18-02-PLAN.md` and `18-03-PLAN.md`, both of which depend on this plan's schema and resolver existing first.

Purpose: every downstream plan in this phase (call-site migration, admin CRUD) depends on `SettlementSplitTier` existing in the DB and `resolveSplit()` being callable — this is the load-bearing plan for the whole phase.

Output: `SettlementSplitTier` Prisma model + migration, `SettlementService.resolveSplit()`, `settle()`'s new NaN guard, and 6 backfilled `SettlementSplitTier` rows in the dev database (one per module, `tierName: 'default'`).

**Discretion note (Claude's Discretion, per CONTEXT.md):** Shadow-verification (a dedicated comparison script diffing old-flat-key vs. new-resolver results) is explicitly optional research guidance, not a locked decision. This phase migrates all 6 call sites together (not partially, unlike the prior SETTLE-09 Transport/Delivery-only cutover that shadow-verify was built for) and each call site's migration plan (18-02/18-03) adds a pre/post-migration regression test asserting identical computed amounts for identical mocked `resolveSplit()` output. That regression coverage is judged sufficient in place of a dedicated shadow-verify script for this phase — a live production shadow-run against real settled rows is not built here.
</objective>
