### Gaps Summary

Gap-closure plan 19-05 fully and correctly closed 2 of the 3 CRITICAL findings from the prior verification/review cycle: CR-02 (raise()'s TOCTOU race, now backstopped by a DB-level partial unique index with a matching P2002-to-ConflictException translation) and CR-03 (raise()'s missing module cross-check, now rejected with BadRequestException before any row is created). Both are independently confirmed correct by reading the live code and running the updated test suite (28/28 unit, 3/3 e2e, 47/47 adjacent settlement-service regression tests, clean `tsc --noEmit`).

The third finding, CR-01 (money-conservation in `computeAdjustmentLines()`), was only partially closed. The specific case the original finding described — the platform wallet's own line never being computed at all — is now fixed via a correct, self-balancing `correctPlatformTotal` formula. But independently reading the function line-by-line (not just trusting the fix's description) surfaces a new variant of the identical bug class, exactly as an independently-run fresh code review documented: `correctPlatformTotal`'s subtraction is unconditional, while the ministry/earner lines it's implicitly counting on are only pushed when a concrete wallet exists to receive them. Whenever a dispute corrects a settlement that lacks a wallet-bearing row for a category the corrected split now assigns a nonzero share to (an unconfigured ministry wallet at original settle-time, or an earner whose original amount was legitimately zero), that category's corrected total is subtracted from the platform's total but never actually posted anywhere — the resulting `lines` array is not zero-sum, and `SettlementService.adjust()` (which has no defensive balance check by design) applies it as-is, silently destroying or manufacturing money with no error, warning, or BLOCKED state. This is not a hypothetical edge case: it is squarely within the scenarios this feature exists to correct (a settlement made under an incomplete or wrong original split), and no fixture anywhere in the test suite (unit or e2e) exercises it — every current fixture with a nonzero ministry/earner percentage also happens to include a matching wallet-bearing row for that category.

Because SETTLE-10c ("resolving a dispute produces a non-destructive adjustment") is a must-have truth and it remains falsifiable for a plausible input shape, this phase's status remains `gaps_found` per the decision tree (any FAILED truth forces this regardless of the overall ratio — now 4/5 rather than the prior 3/5). The fix is well-scoped and mirrors the pattern the 19-05 plan itself already used for the platform side: only "claim" a category's corrected total into `correctPlatformTotal`'s subtraction when that category will actually receive a deliverable line, otherwise retain it on the platform wallet (mirroring `settle()`'s own unresolved-recipient roll-up semantics) — plus 3 targeted regression tests for the trigger paths that are currently unguarded. Separately, the CR-02 fix's real-world effectiveness depends on an as-yet-unconfirmed database migration deployment, which is flagged for human verification since it cannot be checked from source alone.
