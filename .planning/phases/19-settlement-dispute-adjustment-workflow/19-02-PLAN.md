<objective>
Add `SettlementService.adjust()` — the compensating-transaction primitive `SettlementDisputeService.resolve()` (built in `19-03-PLAN.md`) calls to apply a dispute's correction. This is additive only: `settle()`'s signature, behavior, and all 6+1 existing call sites (Transport/Delivery/Marketplace/Events/Stays/Studio/Tour) are untouched.

This plan does NOT touch the `SettlementDispute` Prisma model or any dispute-workflow code — `adjust()` operates purely on `Transaction`/`Wallet`, which already exist, so it has no dependency on `19-01-PLAN.md` and runs in parallel with it in Wave 1.

Purpose: `settle()` is credit-only (it has a defensive floor check that rejects negative recipient amounts outright) and cannot express a claw-back debit. Disputes need a new, general primitive that allows both signs, locks wallets the same safe way, and fails closed (not silently) when a debit would overdraw a wallet.

Output: `SettlementService.adjust()`, exported `SettlementAdjustmentLine`/`SettlementAdjustmentInput` interfaces, and exported `InsufficientAdjustmentBalanceError` class.
</objective>

export class InsufficientAdjustmentBalanceError extends Error {
  constructor(public readonly walletId: string, public readonly shortfallNgn: number) { /* ... */ }
}

export interface SettlementAdjustmentLine {
  walletId: string;
  deltaNgn: number; // positive = credit, negative = debit (unlike settle(), both signs allowed)
}

export interface SettlementAdjustmentInput {
  originalReference: string; // must already exist as a settled Transaction
  module: string;
  lines: SettlementAdjustmentLine[];
  reason: string;
  metadata?: Record<string, unknown>;
}

// Returns the SAME SettlementResult shape settle() returns ({ status, platformAmountNgn, recipientCredits }).
async adjust(input: SettlementAdjustmentInput): Promise<SettlementResult>
// Throws InsufficientAdjustmentBalanceError (typed, catchable via instanceof) if any debit line
// would take its wallet negative. Throws a plain Error if originalReference has no settled
// Transaction row. Returns { status: 'REPLAYED', ... } on idempotent replay (same reference
// prefix already applied) — never throws on a benign duplicate call.

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-------------------|
| T-19-01 | Tampering | `adjust()` (all lines) | mitigate | `Number.isFinite()` guard on every `line.deltaNgn` before `$transaction` is entered — mirrors SETTLE-11d's existing NaN guard on `settle()` |
| T-19-02 | Tampering | `adjust()` debit path | mitigate | insufficient-balance check runs INSIDE the `$transaction`, AFTER `SELECT ... FOR UPDATE` has locked the row (race-safe against a concurrent debit draining the wallet between check and write), and throws a typed `InsufficientAdjustmentBalanceError` that rolls back the whole transaction before any `wallet.update` commits — the exact SETTLE-10d requirement |
| T-19-03 | Repudiation | `adjust()` Transaction rows | mitigate | every adjustment writes a NEW `Transaction` row referencing the original via a `-ADJ-${n}` suffix; original rows are never `UPDATE`'d — full historical trail preserved by construction (SETTLE-10c) |
| T-19-04 | Denial of Service / Replay | `adjust()` idempotency precheck | mitigate | reference-prefix precheck (`${originalReference}-ADJ-`) + P2002 fallback prevents a retried or duplicated `resolve()` call from double-applying the same adjustment against a wallet |
