<objective>
Converge Transport's `completeTrip()` onto the generalized `SettlementService.settle()` (Phase 12), gated behind the `transport.settlement_engine_enabled` `PlatformConfig` flag, so driver/Ministry/platform wallets are credited atomically via the shared engine post-cutover — while the pre-cutover path stays byte-for-byte unchanged and additionally records a Stage-2 shadow comparison for every real completion (SETTLE-03, SETTLE-09).

Purpose: This is the actual driver-payout cutover for Transport — the highest-risk write path in this phase. It must preserve D-01's exact driver-payout formula, switch idempotency to a deterministic reference, and prove (via the shadow comparison) that the new engine agrees with the old one before the flag is ever flipped in production.
Output: `completeTrip()` with a working cutover-flag branch; `transport.service.spec.ts` covering both flag states.

Naming-convention note: `ISY-TRP-${tripId}` (this plan) and `ISY-DLV-${orderId}` (Plan 13-03) are a deliberate, documented deviation from CLAUDE.md's `ISY-<TYPE>-<12-char-uppercase>` reference pattern — they use the raw trip/order UUID rather than a random 12-char suffix because `SettlementService`'s idempotency precheck (`settlement.service.ts:94-103`, `Transaction.reference: { startsWith: '${reference}-' }`) requires a **stable, deterministic** reference per trip/delivery to detect replays (13-RESEARCH.md Pitfall 2). A random suffix would defeat idempotency entirely. Task 1 of this plan appends a Naming Patterns entry to `CLAUDE.md` documenting both this plan's and Plan 13-03's convention in a single edit (13-03 does not also touch `CLAUDE.md`, since both plans run in parallel in Wave 2 and touching the same file in both would create a same-wave file conflict).
</objective>

| Boundary | Description |
|----------|-------------|
| Driver-authenticated HTTP request (`PATCH trips/:id/complete`) → `TransportService.completeTrip()` → `SettlementService.settle()` → Postgres wallet rows | Driver-controlled request timing (including retries after client-side timeout) is untrusted input into a financial write path |
| `completeTrip()` → shared standing Ministry wallet (`resolveMinistryWallet()`) | Wallet now contended by up to 6 modules (Tour, Marketplace, Events, Studio, Stays, and now Transport) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-01 | Tampering / Repudiation | `completeTrip()` → `SettlementService.settle()` | mitigate | Deterministic `ISY-TRP-${tripId}` reference (replacing the random-UUID scheme) feeds `SettlementService`'s `Transaction.reference` prefix precheck (`settlement.service.ts:94-103`) + `P2002` race fallback (`236-253`), so a client retry after a timeout is recognized as a replay, not a second credit |
| T-13-02 | Denial of Service | Ministry wallet lock contention | mitigate | Unchanged — `SettlementService`'s canonical sorted-`walletId` lock order (`settlement.service.ts:151-165`) already prevents deadlock across concurrent settlements sharing the Ministry wallet; Task 1's acceptance criteria forbid Transport from adding its own wallet lock |
