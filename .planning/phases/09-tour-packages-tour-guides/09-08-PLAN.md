<objective>
Implement TOUR-07 (post-tour rating + auto-flag) and TOUR-08 backend (admin review queue). Discretion picks already embedded:

- **@OnEvent('review.created')** for aggregate rating recompute (NOT cron) — synchronous recompute per write is fine for v1; debounce via in-memory `Map<targetId, NodeJS.Timeout>` to coalesce bursts (e.g. 5 reviews in 1 minute -> 1 recompute).
- **Polymorphic Review model** (created in 09-01) so stays/marketplace can later write to the same table.
- **AdminReviewFlag** as a separate model (not just a column) — makes the queue queryable + assignable.

**Photos upload contract (hard dependency on 09-02):** This endpoint does NOT accept inline multipart file uploads. Review photos come in as a `string[]` of publicly-accessible URLs that the client obtained via the presigned-URL flow shipped in plan 09-02:

1. Client (web rating form OR mobile RatingModal) POSTs to `POST /api/v1/uploads/presigned` with `{ keyPrefix: 'review-photos', contentType: 'image/jpeg' | 'image/png' | 'image/webp', maxBytes?: number }` — one call per photo.
2. Server returns `{ uploadUrl, key, publicUrl, expiresIn: 900 }`.
3. Client PUTs the raw image bytes to `uploadUrl`.
4. Client POSTs `/api/v1/reviews` with `{ ..., photos: [publicUrl1, publicUrl2, ...] }` (max 5 photos enforced by DTO `@ArrayMaxSize(5)`).

The CreateReviewDto field validates `@IsUrl({}, { each: true })` — incoming non-URL strings are rejected at the DTO layer. UploadService is the ONLY blessed path for getting a URL into this field; this plan does NOT need to re-implement upload handling. The earlier ROADMAP gap (SC7 "rate the guide with photo") is closed end-to-end: 09-02 ships the presigned URL primitive, 09-08 accepts the resulting publicUrls, 09-09/09-11 ship the picker UX.

**Eligibility rule** (service guard):
- Booking status must be CONFIRMED with `tourDate + durationHours <= now` (tour has ended) OR status CHECKED_OUT.
- Booking.buyerUserId === actorUserId (group leader for split-bill).
- A given booking can produce at most ONE review per (targetType, targetId) combo — enforce via service-level pre-check (`prisma.review.findFirst({ where: { tourBookingId, targetType, targetId } })`).
- targetType GUIDE: targetId must equal booking.tourPackage.tourGuideId (resolve via snapshot).
- targetType PACKAGE: targetId must equal booking.tourPackageId.
- targetType VENUE: targetId must be in (booking.snapshot.attractionIds ∪ [booking.snapshot.propertyId]).

**Aggregate recompute** (per target):
- For each target, `rating = AVG(rating) WHERE targetType=? AND targetId=?` and `reviewCount = COUNT(*)`. Update via:
  - targetType GUIDE -> `prisma.tourGuide.update({ where: { id: targetId }, data: { rating, reviewCount } })`.
  - targetType PACKAGE -> `prisma.tourPackage.update({ where: { id: targetId }, data: { rating, reviewCount } })`.
  - targetType VENUE: try Property first; if not found, try Attraction; if neither, log warn (orphan review — shouldn't happen given the create-guard).

Output: A new `reviews` NestJS module + AppModule registration + spec.
</objective>

Aggregate recompute debounce (in-memory map):
  private pendingRecomputes = new Map<string, NodeJS.Timeout>();
  private scheduleRecompute(targetType, targetId) {
    const key = targetType + ':' + targetId;
    if (this.pendingRecomputes.has(key)) clearTimeout(this.pendingRecomputes.get(key)!);
    this.pendingRecomputes.set(key, setTimeout(() => {
      this.recomputeTargetRating(targetType, targetId).catch(err => this.logger.error('Recompute failed', err));
      this.pendingRecomputes.delete(key);
    }, 5000));   // 5s debounce
  }
