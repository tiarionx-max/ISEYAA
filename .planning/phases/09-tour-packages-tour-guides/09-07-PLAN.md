<objective>
Implement TOUR-05 itinerary delivery — 3 channels, reusing existing primitives:
- (a) In-app structured view — already covered by 09-11 mobile screen reading TourBooking.itinerary.
- (b) Email PDF via SendGrid — generated immediately on `tour_booking.confirmed` event emitted by 09-06.
- (c) Push notifications T-24h, T-2h, T+1h after tour end — cron-scanned hourly/15-min, idempotent via per-booking metadata flags.

All cadence offsets read from PlatformConfig (09-01 seeded `tour.notify_t_minus_24h_hours` and `tour.notify_t_minus_2h_hours`). Per CLAUDE.md anti-pattern: notification offsets are configurable, never hardcoded.

PDF generation: prefer reusing an existing PDF lib if `package.json` has `pdfkit` / `pdf-lib` / similar. If absent, add `pdfkit` (lightweight, no Chrome dep, ~3MB). Render simple A4 doc with header (cover image — fetched via HTTPS), package name, tour date, group size, list of itinerary items with hour offset + title + description + location. Upload via existing S3Service to `s3://${AWS_S3_BUCKET}/itineraries/${bookingId}.pdf`. Persist the resulting CloudFront URL to `Itinerary.pdfUrl`.

Cron uses `@Cron(CronExpression.EVERY_HOUR)` for T-24h (window is wide enough — 23-25h gives a 2h slop) and `@Cron(CronExpression.EVERY_15_MINUTES)` for T-2h and T+1h (tighter windows). Cron scheduling reuses Phase 5 pattern (ScheduleModule is already registered in AppModule per `stays.service.ts:303` and `delivery.service.ts` cron use).

Idempotency: per-booking metadata flags (`notifiedTMinus24h: true`, etc.) prevent double-pushes across cron tick boundaries. Set the flag AFTER successful send.

Output: 1 new common service (PDF) + 1 new module-level service (notifications) + module/common registrations + a spec exercising the cron windows + PDF generation.
</objective>
