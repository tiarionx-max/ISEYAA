<objective>
Ship the scheduled digest itself (MIN-08a, MIN-08c): a once-daily `@Cron` tick, guarded by Phase 20's `setNx()` distributed lock (per CONTEXT.md's "Claude's Discretion" note: "very likely yes — the planner should confirm and apply it, not silently skip it"), that finds every `MinistryExportSubscription` due for its cadence, gathers all 3 existing Phase 14 Ministry reports for that subscription's own rolling window (`lastSentAt ?? createdAt` → now, per D-04), renders one branded multi-section PDF plus one combined CSV, and sends via `SendgridService.sendMinistryDigest()` wrapped in `ResilienceService.execute('sendgrid', ...)` — the exact already-live vendor policy used by OTP email, no new resilience wiring needed.

This plan depends on 22-02's `ministry.module.ts` registration (same file, sequenced to avoid a same-wave file conflict) and 22-01's schema/SendGrid-method foundation.

Purpose: this is the load-bearing plan for MIN-08a/MIN-08c — the digest does not exist end-to-end until this scheduler ties `MinistryService` (data), `MinistryPdfService`/`CsvExportService` (rendering), and `SendgridService.sendMinistryDigest()` (delivery) together on an unattended cadence.

Output: `MinistryExportSchedulerService` with a `checkSubscriptionsDue()` `@Cron` method, registered in `ministry.module.ts`, full test coverage of the lock guard, per-subscription rolling window, size-guard fallback, and success/failure status persistence.
</objective>

## Trust Boundaries

| Boundary | Description |

| `@Cron` tick → SendGrid | Server-initiated, no untrusted input; `subscription.recipients` was already validated at the 22-02 DTO boundary before being persisted |

| Threat ID | Category | Component | Disposition | Mitigation Plan |

| T-22-06 | Denial of Service (double-send) | `checkSubscriptionsDue()` under multi-replica deploy | mitigate | `setNx('cron-lock:checkMinistryExportSubscriptions', ...)` distributed lock — a second replica's tick returns immediately without querying or sending (Phase 20 pattern, applied per CONTEXT.md's discretion note) |
| T-22-07 | Repudiation | Failed/successful digest sends | mitigate | Every attempt updates `lastStatus`/`lastError`/`lastSentAt` on the subscription row (readable via 22-02's `GET` route) AND is `Logger.log`/`Logger.error`'d — satisfies MIN-08c's "every scheduled delivery attempt is logged" |
