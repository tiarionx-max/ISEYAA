<objective>
Build the foundational resilience engine every vendor-call-site plan in this phase depends on: a `@Global()` `ResilienceModule` exporting a `ResilienceService` that constructs one cached cockatiel circuit-breaker + retry + timeout policy per vendor (Paystack, Paystack-refund, Termii-auth, Termii-delivery, Anthropic, S3, FCM) at process startup, reads PlatformConfig-backed thresholds per D-06/D-07 with hardcoded defaults, and wires every breaker state transition to a manual OpenTelemetry span plus a `Sentry.captureMessage` alert per D-09.

Purpose: This is the single choke-point service every other plan in Phase 11 (Paystack/S3, FCM/Anthropic, Termii) calls via `resilience.execute(vendor, fn)`. Getting the per-vendor stateful-breaker construction and PlatformConfig-fallback pattern right here, once, means every downstream plan is a thin wrapping change rather than a re-derivation of circuit-breaker mechanics. `paystackRefund` is split out as its own vendor key (distinct from `paystack`) per RESEARCH.md Pitfall 6: retrying `initiatePayment`/`resolveBvn` on a transient failure is safe, but retrying `refundCharge` after a response is lost risks a double-refund if Paystack's server actually processed the first attempt — this plan defaults `paystackRefund`'s retry count to zero so cockatiel never auto-retries a refund, while still giving it circuit-breaking + timeout + observability.
Output: `cockatiel@^3.2.1` + `@opentelemetry/api@^1.9.1` installed and pinned; `backend/src/resilience/` module (types + service + module) with passing unit tests; `ResilienceService` registered globally in `AppModule`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Backend service → Paystack / Termii / Anthropic / S3-R2 / FCM (external vendor APIs) | Outbound HTTPS calls; vendor response bodies/errors must never leak into client-facing exception messages |
| `ResilienceService` → Sentry / OpenTelemetry exporters | Internal telemetry sink; span attributes and Sentry messages must carry only vendor identifiers and generic error classes, never raw request payloads |
| `ResilienceService` → `PlatformConfig` (Postgres) | Trusted, admin-writable internal config source — not user-controlled input |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-01 | Information Disclosure | Vendor-service exception construction (implemented in Plans 02-04; enabled by this plan's `execute()` facade returning the raw policy error to callers) | mitigate | Callers must construct `ServiceUnavailableException` from a static per-vendor string only, never interpolate `err.response.data`/`err.message` — see Plans 02-04 |
| T-11-02 | Denial of Service (retry amplification against an already-struggling vendor) | `resilience.service.ts` policy composition | mitigate | `ExponentialBackoff({initialDelay:200, maxDelay:3_000})` + circuit breaker fail-fast-when-open (zero calls dispatched while open, not just slower calls) — implemented in Task 2 |
| T-11-03 | Information Disclosure (PII in observability payloads) | `resilience.service.ts` `onBreak`/`onReset`/`onHalfOpen` handlers | mitigate | Span attributes and `Sentry.captureMessage` calls carry only `vendor` name + generic error class/message string — never the raw `reason.error` object's nested request/response payload (which could contain phone numbers, BVNs, tokens); matches the existing `paystack.service.ts:68` "Never log the BVN value" convention |
| T-11-04 | Denial of Service (false-positive circuit trip from bad user input) | `resilience.service.ts` `isTransientError` filter | mitigate | `handleWhen(isTransientError)` excludes 4xx business-logic errors (invalid BVN, duplicate Paystack reference, etc.) from counting toward the breaker's failure threshold — verified by Task 2's dedicated test case |
| T-11-05 | Repudiation / financial-integrity risk (double-refund from an automatically retried, ambiguous-outcome refund call) | `resilience.service.ts` `paystackRefund` vendor policy | mitigate | `RESILIENCE_DEFAULTS.paystackRefund.retryCount = 0` — cockatiel never automatically retries a refund call; a lost response after a server-side-successful refund surfaces as a single failed attempt (D-01 fail-loud), not a silent second refund. Verified by Task 2's dedicated zero-retry test case |
</threat_model>
