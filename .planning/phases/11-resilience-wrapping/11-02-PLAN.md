<objective>
Wrap the two centralized, single-choke-point vendor services — `PaystackService` (initiatePayment/resolveBvn/refundCharge) and `S3Service` (upload) — in the `ResilienceService` policy built in Plan 01, converting any circuit-open/timeout/retry-exhausted failure into the D-01/D-05 fail-fast `ServiceUnavailableException` contract while preserving each method's existing business-error paths untouched.

Purpose: Both services are already accessed through a single method per call type across the whole codebase (6 S3 callers, all wallet/refund Paystack flows), so wrapping at the service-method level satisfies "every call site" for these two vendors without touching any caller. `refundCharge()` uses the distinct `paystackRefund` vendor key (built in Plan 01 with `retryCount: 0`) rather than sharing `initiatePayment`/`resolveBvn`'s `paystack` key — per RESEARCH.md Pitfall 6, automatically retrying a refund whose response was lost risks a double-refund if Paystack's server actually processed the first attempt.
Output: `paystack.service.ts` and `s3.service.ts` route their outbound HTTP calls through `resilience.execute()`; new `paystack.service.spec.ts` test file; extended `s3.service.spec.ts`.
</objective>

| T-11-01 | Information Disclosure | `paystack.service.ts` (`initiatePayment`/`resolveBvn`/`refundCharge` catch blocks), `s3.service.ts` (`upload` catch block) | mitigate | Every `ServiceUnavailableException` thrown in this plan is constructed from a static per-vendor string literal — `err.response.data`/`err.message` are logged server-side via `this.logger.error(...)` only, never interpolated into the thrown message (verified by Task 1/2 acceptance criteria) |
