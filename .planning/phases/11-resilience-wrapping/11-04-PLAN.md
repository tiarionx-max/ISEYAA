## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Backend → Termii API (`v3.api.termii.com`) — two independent call sites | Outbound HTTPS carrying phone numbers + OTP codes; response bodies must never leak into logs beyond generic status/error class |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-11-03 | Information Disclosure (PII — phone numbers in Termii error logs) | `auth.service.ts` `sendTermii` catch block, `delivery.service.ts` `sendTermiiDeliveryOtp` catch block | mitigate | Both existing catch blocks already log only `err` (the fetch/network error object) via `Logger.error`, never the request body containing the phone number or OTP — this plan does not change what is logged, only routes the call through `resilience.execute` first; the vendor-name-only discipline from Plan 01's `onBreak` handler applies identically to `'termiiAuth'`/`'termiiDelivery'` |
| T-11-04 | Denial of Service (cross-tenant lockout via shared Termii circuit) | Independent `termiiAuth`/`termiiDelivery` vendor keys | mitigate | Per D-07/D-08, auth OTP and delivery OTP use SEPARATE cockatiel policy instances (`'termiiAuth'` vs `'termiiDelivery'`) — a Termii outage affecting delivery OTP cannot open the auth OTP circuit and vice versa, even though both hit the same upstream Termii API |

See Plan 01's `<threat_model>` for the shared retry-amplification (T-11-02) mitigation implemented once in `ResilienceService` and inherited here.
