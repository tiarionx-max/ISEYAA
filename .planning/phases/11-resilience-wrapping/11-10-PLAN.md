<objective>
Close WR-01 and the notifications.service.ts slice of WR-02 from `11-REVIEW.md` (fresh code review of the gap-closure batch that produced `11-VERIFICATION.md`'s primary finding, addressed separately in Plan 11-09).

**WR-01:** `NotificationsService.registerToken` (`notifications.service.ts:57-63`) overwrites the entire `User.metadata` JSON blob with `{ fcmToken: token }` on every call instead of merging. Nothing else currently writes other keys into `metadata`, so there is no observable data loss today — but it is a latent trap: the next feature that stores anything else in `user.metadata` (preferences, device info, etc.) will have its data silently wiped every time a user re-registers an FCM token (e.g. on every app relaunch). Fix per 11-REVIEW.md: read-then-merge before the `update()` call.

**WR-02 (notifications.service.ts slice):** `paystack.service.spec.ts`'s Test 7 is the only one of six resilience-wrapped-call spec files that asserts AbortSignal reference-identity (that the *exact same* signal instance cockatiel provides reaches the underlying vendor call). `notifications.service.spec.ts` does not. Add that assertion for `sendPush`'s axios call, mirroring paystack's pattern.

Purpose: Close a latent data-integrity trap before any future feature relies on `User.metadata` for anything beyond `fcmToken`, and close a test-coverage gap that would let a future refactor silently drop AbortSignal forwarding in `sendPush` without any test catching it.
Output: `registerToken` merges instead of overwrites; two new tests proving the merge behavior; one new test proving AbortSignal reference-identity for `sendPush`.
</objective>
