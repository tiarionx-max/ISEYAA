<objective>
Wire the third and most complex D-01 visitor-entry capture point: Tour Bookings. Unlike Events (real-time scan) and Stays (single confirmation event), Tour Bookings has TWO distinct code paths that transition a booking to `CONFIRMED` — solo/group (single payment) and split-bill (N independent share payments, CONFIRMED only once all N have paid) — and both must write exactly one `VisitorLog` row, never zero, never more than one. `TourPackage.lgaId` is nullable (schema.prisma:950) and must be handled without throwing. Also thread the optional `purpose` field (D-06) through `CreateTourBookingDto` into `TourBooking.metadata`, and avoid RESEARCH.md's documented module-string trap (`'tour_booking'` in `Transaction.metadata.module` vs `'tour'` in `TourBooking.metadata.module` — irrelevant to this plan's writes, but do not introduce a third variant).

Purpose: Completes the write side of MIN-02/MIN-03's three data sources (Events + Stays landed in Plan 14-04). This plan's `TourPackage.lgaId` and `buyer.role` lookups happen once per confirmed booking (not once per settlement recipient), keeping the extra query cost negligible on a low-frequency confirmation path.
Output: `TourBookingService.createTourBooking()` persists `dto.purpose`; `TourSettlementService` writes exactly one `VisitorLog` row per confirmed booking from a single shared helper, covering both the solo/group and split-bill-final code paths.
</objective>
