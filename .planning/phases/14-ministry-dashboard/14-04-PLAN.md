## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Ticket buyer / booking guest (authenticated user) → `purpose` DTO field | Free-form-adjacent input, constrained to the fixed `VISITOR_PURPOSE_VALUES` allowlist at the DTO layer — not free text |
| Check-in / payment-webhook handlers → `VisitorLogService.record()` | First-party in-process call; a write failure must never regress the primary flow (ticket check-in, booking confirmation email) |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-14-07 | Tampering | `purpose` DTO field accepting arbitrary strings | mitigate | `@IsIn(VISITOR_PURPOSE_VALUES)` rejects any value outside the fixed 7-item taxonomy at the validation-pipe boundary, before it ever reaches `Ticket.metadata`/`Booking.metadata` |
| T-14-08 | Denial of Service | A `VisitorLog` write failure cascading into a check-in/booking-confirmation failure | mitigate | Both write sites wrap `visitorLogService.record()` in its own `.catch()` that logs and swallows — mirrors `handleStayPayment()`'s existing method-level error-handling convention; a Ministry-analytics write failure can never block a revenue-generating flow |
</threat_model>
