<research_findings>
These findings come from direct codebase investigation and WebFetch attempts against Flutterwave's live
developer docs, done during planning. Read carefully before executing Task 1 — they materially change what
"verify via WebFetch" means for this migration.

1. **Flutterwave's public docs have moved to a v4 API** (`developersandbox-api.flutterwave.com`, resource
   model: `customers` -> `payment-methods` -> `charges`, webhook header `flutterwave-signature` verified via
   HMAC-SHA256 base64). Every v3-specific doc URL attempted during planning 404's on Flutterwave's live site
   (the v3 doc tree appears to have been removed from public docs, not just restructured).
2. **This task targets v3, not v4** — per the explicit task brief ("using Flutterwave's real v3 API") and
   because this repo's existing `webhooks.service.ts::handleFlutterwave` (already implemented, working,
   pre-dates this task) already uses the v3-style `verif-hash` header + literal secret-hash string comparison,
   NOT v4's HMAC scheme. Flutterwave's v3 API (`api.flutterwave.com/v3/...`) remains operationally live for
   existing integrations even though it's no longer the featured public doc — this is a legacy-but-supported
   API tier, not a deprecated/dead one.
   **Task 1 must still attempt a fresh WebFetch against Flutterwave's docs first** (things change — try
   `https://developer.flutterwave.com/docs/collecting-payments/standard-payments`,
   `https://developer.flutterwave.com/reference/create-charge`, and search `https://developer.flutterwave.com/llms.txt`
   for any surviving "v3" or "standard payment" reference). If v3 docs are reachable, use them as the source of
   truth. If they still 404 (matching planning-time findings), use the fallback shapes below — they are
   cross-checked against this repo's own existing v3-style webhook implementation, which independently
   corroborates the v3 scheme is what's intended here.
   **Do NOT adopt v4's `customers`/`payment-methods`/`charges` flow or its `flutterwave-signature` HMAC-SHA256
   webhook scheme** — that is an architecturally different integration, out of scope for this migration, and
   would break the already-correct `handleFlutterwave` webhook handler.

3. **Fallback v3 API shapes** (use if WebFetch confirms v3 docs are still unreachable):
   - Initialize payment: `POST https://api.flutterwave.com/v3/payments`
     Headers: `Authorization: Bearer <FLUTTERWAVE_SECRET_KEY>`, `Content-Type: application/json`
     Body: `{ tx_ref, amount, currency: 'NGN', redirect_url?, customer: { email }, meta }`
     Response: `{ status: 'success', data: { link: '<checkout url>' } }` — no `access_code` equivalent exists.
   - Verify by reference (NEW method, not present on PaystackService — see point 4):
     `GET https://api.flutterwave.com/v3/transactions/verify_by_reference?tx_ref=<ref>`
     Response `data`: `{ id: <number>, tx_ref, status: 'successful'|'failed'|'pending', amount, currency, card?: { token?, first_6digits?, last_4digits? } }`
   - Refund: `POST https://api.flutterwave.com/v3/transactions/{id}/refund` — **requires Flutterwave's own
     numeric transaction `id`, NOT the tx_ref string.** Paystack's refund took the reference string directly;
     Flutterwave does not. `refundCharge()` must first call verify-by-reference to resolve `data.id`, then
     POST the refund to `/v3/transactions/{id}/refund` with optional body `{ amount }`. Response
     `data: { id, amount_refunded, status }`.
   - Tokenized (recurring) charge — replaces Paystack's `chargeAuthorization`:
     `POST https://api.flutterwave.com/v3/tokenized-charges`
     Body: `{ token, currency: 'NGN', country: 'NG', amount, email, tx_ref }`
     Response `data`: `{ status: 'successful'|..., tx_ref }`. The `token` comes from a prior successful
     transaction's `data.card.token` (captured by the existing webhook handler — see point 5).
   - BVN resolve: `GET https://api.flutterwave.com/v3/kyc/bvns/{bvn}` (lower confidence on exact path/casing
     than the other endpoints above — Task 1 MUST attempt a live WebFetch specifically for this one before
     falling back; if unreachable, implement against this shape but flag the uncertainty explicitly in the
     plan SUMMARY). Response `data`: `{ first_name, last_name, date_of_birth? }`.

4. **`verifyTransaction` is new functionality, not a 1:1 Paystack port.** PaystackService never had a verify
   method (Paystack verification happened purely via webhook signature). Flutterwave's own webhook docs
   explicitly recommend re-querying the API before trusting webhook data ("always re-query our API to verify
   the transaction details"). Add `verifyTransaction(txRef)` to FlutterwaveService as part of its method
   surface (the task brief names "initialize/verify transaction" explicitly). Wiring it into
   `handleFlutterwave` as a defense-in-depth re-query is a genuine improvement directly enabled by this method
   — do it if it fits cleanly in Task 1/2's budget; if not, it's still fine to ship `verifyTransaction` as an
   available method without forcing a webhook rewrite (the existing webhook signature check is already the
   primary trust boundary).

5. **`webhooks.service.ts::handleFlutterwave` already exists, already works, and needs NO behavioral changes**
   for its core signature/dispatch logic. It already: verifies via `timingSafeEqual` string comparison,
   normalizes naira->kobo for downstream handlers, and dispatches all payment types including
   `wallet_topup` -> `creditWallet(..., 'wallet', 'FLUTTERWAVE')`. The ONLY real bug found during planning:
   it reads `this.config.get('FLUTTERWAVE_SECRET_KEY')` as the webhook secret-hash comparison value — this is
   WRONG. Flutterwave's dashboard has a separate "Secret Hash" field (an arbitrary string you set yourself),
   distinct from the API secret key. Fix: read a new `FLUTTERWAVE_WEBHOOK_SECRET_HASH` env var instead
   (mirrors `PAYSTACK_WEBHOOK_SECRET` being distinct from `PAYSTACK_SECRET_KEY`). This is squarely in scope —
   the task brief explicitly names "webhooks.service.ts: verify Flutterwave's webhook signature... secret-hash
   comparison" as scope item 2.

6. **`POST /webhooks/paystack` must be removed entirely** (not left dormant) per the full-migration
   requirement — once nothing initiates a Paystack charge, nothing will ever deliver a `charge.success`
   webhook to it. `handlePaystack()` and the controller route are dead code the moment Task 2 lands; delete
   both rather than leaving an unreachable stub.

7. **Deliberately NOT renamed (flagged, not guessed away) — DB schema identifiers containing "paystack":**
   `Booking.paystackRef`, `Membership.paystackRef` / `paystackAuthCode` / `paystackEmail`, and 2 other
   `paystackRef` columns across `schema.prisma` (grep confirms 6 total column declarations). These are live
   Prisma-mapped Postgres columns on a production database. Renaming them requires a schema migration
   (`prisma migrate dev`) against real data — genuinely riskier than leaving the legacy names in place, and
   out of scope for a "code migration only" task with no live DB access in this environment. **Do not rename
   them.** They will hold Flutterwave values going forward (tx_ref in `paystackRef` columns, card `token` in
   `paystackAuthCode`) — add a one-line comment at each Prisma field declaration noting this, and do NOT touch
   `schema.prisma` beyond adding those comments (no migration, no `prisma generate` needed — the `String`
   types are unchanged).
8. **`PaymentGateway` enum in schema.prisma already has both `PAYSTACK` and `FLUTTERWAVE` values** (lines
   155-160) — no schema change needed to make Flutterwave a valid gateway. **Do not remove `PAYSTACK` from the
   enum** — historical `Transaction` rows already tagged `gateway: PAYSTACK` must remain valid/readable; only
   the *default* used by new writes changes.
9. TS-level (not DB-level) identifiers that ARE safe and appropriate to rename in this task, since they're
   pure interface/type names with all usages inside files this plan already touches: `RefundInput.paystackReference`
   -> `RefundInput.gatewayReference`, `RefundResult.paystackRefundId` -> `RefundResult.gatewayRefundId` (in
   `refund.service.ts` + its 2 spec-file call sites), and the `'PAYSTACK' | 'FLUTTERWAVE' | ...` gateway
   default parameters in `wallet.service.ts` (`debitWallet`, `creditWallet`) and `refund.service.ts` change
   their *default value* from `'PAYSTACK'` to `'FLUTTERWAVE'` (the union type itself keeps `'PAYSTACK'` as a
   legal value, per point 8).

| Flutterwave webhook -> WebhooksController | Untrusted inbound HTTP from Flutterwave's infrastructure carrying payment-success claims that trigger wallet credits and settlement |
| ISEYAA backend -> Flutterwave API | Outbound calls carrying the live secret key and (for BVN) citizen PII (raw BVN digits) |
| KycService -> FlutterwaveService.resolveBvn | Citizen BVN crosses from internal DB lookup to an external gateway call |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-260819-01 | Spoofing | `handleFlutterwave` webhook | mitigate | Fix the pre-existing bug where the webhook secret-hash comparison reused `FLUTTERWAVE_SECRET_KEY` (the API auth key) instead of a dedicated `FLUTTERWAVE_WEBHOOK_SECRET_HASH` — reusing the API key means anyone who ever saw the API key (e.g. via a compromised outbound-call log) could forge webhooks; a dashboard-set secret hash is a separate, rotatable credential (Task 2). |
| T-260819-02 | Tampering | `handleFlutterwave` -> wallet credit | accept | Amount/status still come directly from the (now-correctly-verified) webhook body without a mandatory re-query. `verifyTransaction` is added to FlutterwaveService (Task 1) as available defense-in-depth but wiring it into every dispatch path is not made a hard blocking requirement this task — the existing `timingSafeEqual` secret-hash check plus reference-based idempotency in `creditWallet` already bound the blast radius of a forged/replayed webhook to "any attacker who already has the correct secret hash," which is the same trust level Paystack's HMAC scheme provided. |
| T-260819-03 | Information Disclosure | `FlutterwaveService.resolveBvn` | mitigate | Never log the raw BVN value (mirrors PaystackService's existing "Never log the BVN value" comment/behavior) — carried forward verbatim in Task 1. |
