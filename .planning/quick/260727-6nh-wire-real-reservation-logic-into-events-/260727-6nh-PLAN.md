<objective>
Two related gaps intentionally left open by an earlier whole-codebase bug sweep, now scoped for a real fix per user decision:

1. **events-service / stays-service gRPC reservation stubs**: `EventsGrpcController.ReserveTicket` and `StaysGrpcController.CreateBooking` currently only READ a pre-existing PENDING row via Prisma — they never actually reserve anything or talk to Paystack. This plan extends the proto contracts (adds `email` to both requests, `guests` to the booking request, and Paystack authorization fields to both responses) and rewires both gRPC handlers to delegate to the real `EventsService.purchaseTicket` / `StaysService.createBooking` HTTP-layer methods, following the same in-process-service-injection pattern already proven by `wallet-grpc.controller.ts` + `WalletModule`.

2. **Event-approval feature**: `Event.status` has a full `DRAFT → PENDING_APPROVAL → APPROVED → PUBLISHED` lifecycle in the Prisma enum, and `AdminService.getDashboard()` already counts `PENDING_APPROVAL` events into `pending_approvals` — but nothing anywhere ever transitions an event out of `DRAFT`. This plan builds the missing organizer-submit + admin-approve workflow end to end and wires it into the existing `admin-grpc` `ApproveItem` RPC (which currently no-ops for `itemType: 'event'`).

Purpose: Replace two fake/no-op code paths with real, tested business logic, closing out the last two "needs design decision" items from the prior bug sweep (the third, Flutterwave, is explicitly out of scope — leave as-is).
Output: Real ticket/booking reservation over gRPC with live Paystack payment initiation; a working DRAFT→PENDING_APPROVAL→PUBLISHED event approval workflow reachable from both REST and gRPC.
</objective>
