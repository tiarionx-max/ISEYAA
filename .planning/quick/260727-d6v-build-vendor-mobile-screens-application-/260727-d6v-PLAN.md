## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Mobile app → `POST`/`PATCH`/`DELETE /products*` | Vendor-supplied product data (name, price, stock, category, compareAtPrice) crosses into Prisma writes, scoped server-side to the caller's own vendor record |
| Mobile app → `PATCH /orders/:id/status` | Vendor-triggered fulfillment status transition |
| Mobile app → `PATCH /users/me/role` | Client-triggered active-role change, silently invoked by `ensureVendorRole` |
| Mobile app → `GET /vendors/me`, `GET /products/mine`, `GET /orders/vendor` | Must never return another user's vendor profile, products, or orders |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-quick-01 | Tampering (enum bypass on `category`) | `CreateProductDto`/`UpdateProductDto` (existing, unmodified) | mitigate | `@IsIn(['fashion','crafts','food','art','tech','agriculture'])` already validates server-side; global `ValidationPipe` (`whitelist: true, forbidNonWhitelisted: true`) strips unknown fields — mobile's `Chip` picker only ever sends one of the 6 allowed values or `undefined`, matching this contract exactly |
| T-quick-02 | Elevation of Privilege (invalid order-status transition) | `PATCH /orders/:id/status` (existing, unmodified) | accept | The backend's hardcoded `allowedTransitions` map (`PROCESSING→SHIPPED`, `SHIPPED→DELIVERED` only) is the real enforcement boundary, already live and out of scope for this plan; the mobile UI showing only the single valid next-status button is a UX affordance to avoid needless 400s, not itself the security control |
| T-quick-03 | Elevation of Privilege (cross-vendor data access) | `GET /vendors/me`, `GET /products/mine`, `GET /orders/vendor` (existing, unmodified) | accept | Each handler resolves the vendor id exclusively from the authenticated JWT subject server-side (`findMyVendor(user.userId)` then scoping products/orders by that vendor's id) — no client-supplied vendor id is ever accepted; unmodified by this plan |
| T-quick-04 | Elevation of Privilege (client-triggered role switch) | `ensureVendorRole` → `PATCH /users/me/role` | accept | `UsersService.switchRole` independently validates server-side that the requested role is already present in the caller's `registeredRoles` (`ForbiddenException` otherwise) — the mobile-side silent call cannot grant VENDOR to a user who was never approved via `PATCH /admin/vendors/:id/approve`, it only re-selects an already-granted role |
