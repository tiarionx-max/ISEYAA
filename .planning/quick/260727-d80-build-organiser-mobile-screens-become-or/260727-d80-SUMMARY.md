# Quick Task 260727-d80: Organiser Mobile Screens (Become-Organiser, Event CRUD, Analytics) Summary

**Four new mobile screens (organiser-dashboard, event-create, event-edit/[id], event-analytics/[id]) plus a single new profile.tsx menu entry give organisers a complete self-service event-management workflow — become an organiser with one tap, create/edit/delete/submit events, upload cover photos, and view real ticket-sales analytics, entirely through UI that did not exist before this task.**

## Performance

- **Duration:** ~50 min (including a worktree base-correction and a full `npm install` to populate a previously-empty `node_modules`)
- **Started:** 2026-07-27 (session start, after worktree ancestry check)
- **Completed:** 2026-07-27
- **Tasks:** 2 completed
- **Files modified:** 6 (4 new, 2 modified)

## Accomplishments

- `organiser-dashboard.tsx` renders a "Become an organiser" gate (`POST /users/me/become-organiser`, no approval wait) when the user lacks the role, and — once granted — a real dashboard listing `GET /events/mine` across all six `EventStatus` values, each visually distinguished by a `StatusBadge`, with an Add-event CTA and per-event Edit / Submit-for-approval (DRAFT-only) / View-analytics actions
- `profile.tsx` exposes exactly one new, always-visible "Organiser Tools" menu row reaching `/organiser-dashboard` — no conditional CTA card, avoiding the merge-conflict-prone pattern used elsewhere in this file
- `event-create.tsx` posts a `CreateEventDto`-shaped body to `POST /events` (always lands `DRAFT`, never auto-submitted for approval), then offers an optional inline cover-photo upload step before returning to the dashboard
- `event-edit/[id].tsx` pre-fills from `GET /events/:id`, saves via `PATCH /events/:id`, supports add-more-photos, a DRAFT-only conditional submit-for-approval action, and a confirmed (`Alert.alert`) delete action
- `event-analytics/[id].tsx` renders `tickets_sold`, `revenue` (Naira via `formatCurrency`), `check_in_rate` (multiplied ×100 for display as a percentage), and `hourly_sales_chart` as a simple `View`-based bar-list (no new charting dependency)
- `mobile/app/_layout.tsx` registers all four new routes immediately after the existing `events/[id]` screen
- Zero backend files were touched
