<objective>
Add the missing Prisma relation between `Order` and `Vendor` (Order.vendorId is already a nullable FK column with an index, but has no `@relation` field on either side) and refactor `MarketplaceService.handleOrderPayment` to resolve the paying order's vendor via `include: { vendor: ... } }` instead of a manual `prisma.vendor.findUnique({ where: { id: order.vendorId } })` call.

Purpose: The current code works around the missing relation with an extra round-trip query and a stale comment claiming "Order.vendorId has no Prisma relation defined ... no DB constraint." Wiring the relation removes that extra query, lets Prisma enforce referential integrity going forward, and matches the pattern already used for `Order.user`.
Output: `schema.prisma` gains an optional `Order.vendor` relation (and `Vendor.orders` back-relation); `marketplace.service.ts`'s `handleOrderPayment` fetches `vendor: { select: { userId: true } }` in the same `order.findUnique` call and reads `order.vendor?.userId` instead of doing a second query.
</objective>

```typescript
async handleOrderPayment(payload: { reference: string }) {
  try {
    const order = await this.prisma.order.findUnique({
      where: { paystackRef: payload.reference },
      include: {
        user: { select: { email: true, firstName: true } },
        orderItems: { include: { product: { select: { name: true } } } },
      },
    });

    if (!order || order.status !== 'PENDING') return;

    // Order.vendorId has no Prisma relation defined (only a raw FK column, no
    // DB constraint — see 12-04 deviation notes), so the vendor is resolved via
    // a direct lookup rather than `include: { vendor: true }`.
    const vendor = order.vendorId
      ? await this.prisma.vendor.findUnique({ where: { id: order.vendorId } })
      : null;
    const vendorWallet = vendor
      ? await this.prisma.wallet.findUnique({ where: { userId: vendor.userId } })
      : null;
    ...
```
