<objective>
Fix a hard PostgreSQL SQL-language violation in the Phase 9 migration `20260623120000_phase9_tour_packages`: it defines a CHECK constraint containing a correlated subquery (`SELECT SUM(...) FROM jsonb_array_elements(...)`), which Postgres unconditionally rejects (error 0A000). Because DDL migrations run in a transaction, this single failing statement rolls back the *entire* migration — meaning none of the 6 Phase 9 tables (tour_guides, tour_packages, tour_bookings, itineraries, reviews, admin_review_flags) have ever actually been created wherever `prisma migrate deploy` ran, despite ROADMAP.md marking Phase 9 complete.

Purpose: Unblock Phase 9 tables from ever being created (locally and eventually in any environment using `migrate deploy`), while preserving the exact original business rule (sum of `settlementSplit[].percentage` <= 100, NULL/empty allowed) using an IMMUTABLE SQL function instead of an inline correlated subquery — since Postgres permits CHECK constraints to call functions, just not to embed subquery syntax directly.

Output: New forward migration directory `backend/prisma/migrations/20260713140000_fix_tour_packages_split_sum_check/migration.sql`. No `schema.prisma` changes (raw CHECK constraints aren't modeled there, matching how the original constraint was hand-authored). No application code changes.
</objective>

```sql
-- ─── CHECK constraint: sum(settlementSplit[].percentage) <= 100 ─────────────

ALTER TABLE "tour_packages" ADD CONSTRAINT "tour_packages_split_sum_check" CHECK (
    COALESCE(
        (SELECT SUM((elem ->> 'percentage')::numeric)
         FROM jsonb_array_elements("settlementSplit") AS elem),
        0
    ) <= 100
);
```
