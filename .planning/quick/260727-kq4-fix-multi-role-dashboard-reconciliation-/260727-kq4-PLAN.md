<objective>
Close a multi-role dashboard reconciliation gap: `host-dashboard.tsx`, `vendor-dashboard.tsx`, `organiser-dashboard.tsx`, and `driver-dashboard.tsx` each fetch their primary listing data immediately on mount without first reconciling the user's single active `role` field to the role the dashboard requires. `RolesGuard` checks only that single active `role` (not `registeredRoles[]`), so a multi-role user whose most-recently-activated role differs from the dashboard they're viewing gets 403'd on read, even though they legitimately hold that role. This is a read-side gap — each screen's own MUTATIONS already reconcile correctly via a local `ensureXRole` helper (established pattern, most recently touched by quick task 260727-jtm); this task extends the exact same reconciliation to each dashboard's initial read query.

Purpose: A host who becomes an organiser (or any other subsequent role switch) must still be able to open their host dashboard and see their properties, without manually switching back to HOST first. Same for vendor/organiser/driver.
Output: All 4 dashboards reconcile their required active role exactly once on mount (via a `roleReconciled` boolean gate, never one reconciliation call per query) before firing any role-gated read query.

Mobile-only, no backend changes — `RolesGuard`'s single-active-role check is correct and unchanged; this is purely proactive client-side reconciliation before reads, mirroring the existing pattern already used before writes.

This plan has 2 tasks with zero file overlap (host+vendor vs organiser+driver) — either order is fine.
</objective>
