<objective>
Found while investigating why a user's registration OTP never arrived by email in production, with no error shown anywhere: `sendOtp()`'s fallback chain (EMAIL → SMS/Termii → Twilio) silently swallowed every failure. `sendTwilio` caught its own errors and just logged them; `sendTermii` fell through to a "stub" log line on total failure; `dispatchOtp`'s catch block called `sendTermii` as a fallback but never checked whether THAT also failed. End result: `POST /auth/otp/send` returned `200 {"message":"OTP sent successfully"}` even when literally no channel delivered anything — exactly what happened in production (Resend domain unverified, Termii timing out, Twilio trial-restricted, all three failing simultaneously with zero visible error).

Purpose: A user facing this exact multi-provider outage in the future gets a clear error instead of silently waiting for a code that will never arrive.
Output: `sendTermii`/`sendTwilio` now return `Promise<boolean>` reflecting actual delivery status. `dispatchOtp` throws `ServiceUnavailableException` when every channel it attempted (with real credentials configured) fails. The local-dev "no credentials at all configured" stub-log path is preserved as a soft-success (unaffected — that's intentional dev convenience, not a failure).
</objective>

</context>
